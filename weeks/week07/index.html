WEEK 07

像工程師一樣開發：規劃與測試

這週先看軟體工程：瀑布式開發（Waterfall Model）一階一階往下流，錯在需求就得逆流回到最上面；測試驅動開發（TDD）把它切成很多小步，先寫測試、再寫程式，其實就是我們一直在用的 VERIFY.md。補充教材再把自己的網站拆開來看：HTML、CSS、JS 和素材各管什麼，瀏覽器怎麼把它們組起來；以及 Git 的版本管理怎麼成為用 AI 開發時的安全網：先看 AI 改了什麼，改壞了就回到上一個存檔點，測試全綠才 commit。

影片 02軟體工程與測試驅動開發（TDD）

  1. AI 寫程式這麼快，為什麼還要軟體工程？軟體工程是一群人在有限的時間裡，做出可靠、以後還改得動的軟體的方法。AI 讓寫程式變快了，難的變成「知道要做什麼」和「確定做對了」，所以軟體工程反而更重要。

  2. 瀑布式開發（Waterfall Model）：一階一階往下流。需求 → 設計 → 實作 → 測試 → 維護。其實你已經跑過一次小瀑布了：BRIEF.md、PLANS.md、Codex 寫程式、VERIFY.md、AGENTS.md。

  3. 問題是測試排在最後。如果錯在需求，就得逆流回到最上面，中間做的全部要重來。最常被引用的瀑布論文（Royce，1970）其實在提醒：只跑一趟「risky and invites failure」。所以業界採用瀑布式開發的，通常是流程很熟、做過很多次、有過去經驗的專案。

  4. 測試驅動開發（Test-Driven Development，TDD）：把一趟大瀑布，切成很多小瀑布。每一小步都是：紅，先寫一個會失敗的測試；綠，寫剛好讓它通過的程式；重構（refactor），把程式整理乾淨，燈要一直是綠的。

  5. 寫測試，就是先寫下「給什麼輸入，應該得到什麼」。一條就是一個測試案例（test case），寫成程式，一個指令全部跑完。是不是很熟悉？這就是我們一直在用的 VERIFY.md。從 Single-turn Prompting 到 VERIFY.md，我們一直強調：先想清楚，結果才有確定性。

  6. 為什麼特別適合 AI：AI 很會說「做好了」，測試不會被說服。回歸（regression）是改了 A，壞了 B：新加「補考」的規則後，原本會過的「請假」測試變紅了；測試每次都全部重跑，B 一壞馬上被抓到。小心 AI 為了通過去改測試，在 AGENTS.md 寫上「不要為了通過而修改測試；覺得測試錯了，先問我」。影片裡的山谷、Codex 畫面和成績都是示意。

補充 1網站是怎麼組成的

  1. 網站像一棟房子。HTML 是隔間：網站的結構和內容（index.html）；CSS 是裝潢：顏色、排版，還有手機版怎麼排（style.css）；JS 是水電和開關：按了會怎樣、地圖、讀資料（app.js）；再加上素材：圖片，還有 CSV、JSON 這些資料。

  2. 拆開自己的網站，就知道每一塊管什麼。拿掉 CSS，內容都還在，只剩瀏覽器預設的樣子，一排一排的字；拿掉 JS，地圖不見了，按鈕按了也沒反應；兩塊都拿掉，剩下的就是 HTML 的隔間和內容。

  3. 網站就是一個資料夾。入口預設叫 index.html：瀏覽器先拿到它，它再把 CSS、JS、圖片、資料一起拉進來。上線，就是把這個資料夾放到網路上。

  4. 瀏覽器就是網頁的「編譯器」。第一堂課裝 Python，是為了讓電腦有能執行 Python 的「編譯器」，把程式碼翻譯給電腦執行（嚴格說，Python 用的是「直譯器」）。做網站不用另外裝：瀏覽器讀 HTML、CSS，執行 JS，裡面是排版引擎和 JS 引擎，有瀏覽器就看得到結果。

  5. 靜態像印好的菜單，動態像現點現做。靜態網站也能互動。Week 6 的考試是靜態網站：進度存在你的瀏覽器裡，換一台電腦就不見了；要跨裝置同步，才需要伺服器和資料庫。

  6. 懂了網站的組成，才控制得住 AI。指令會更準，例如「只改 style.css，不要動 HTML 結構」；出問題時知道是哪一塊；也知道登入、全班共享資料這些事，需要伺服器。影片裡的示範網站和 Codex 畫面是示意。

補充 2Git：版本管理，也是你的安全網

  1. Git 最重要的是版本管理。沒有版本管理的時候，檔案只能存成「報告_final_v2_真的最終.docx」，哪一份是最新的、改了什麼，都很難說。用 Git，每次 commit 就是一個存檔點：可以看歷史、比較差異，回到任何一版。GitHub 只是把這些版本放到雲端。

  2. AI 一次會改好幾個檔案，先看它改了什麼。Codex app 的「檢視變更」會列出這一輪改了哪些檔案：紅色是刪掉的，綠色是加上的；選「最近一輪」，就只看 AI 這一次改的。專案要是 Git 倉庫，才看得到。

  3. 改壞了很正常，回到上一個存檔點就好。直接跟 AI 說：「剛剛這一輪把地圖弄壞了，請還原這一輪的修改，回到上一個 commit。」幾個檔案會一起回到上一個存檔點。

  4. 測試全綠就 commit，說明要寫清楚。跑測試有紅燈，就請 AI 修，再跑一次；全部通過再 commit。說明寫做了什麼、結果怎樣，例如「地圖加上散步路線規劃，測試全部通過」，而不是「update」，之後看歷史、要回去的時候，才找得到這一版。

  5. 影片裡的畫面是示意。示範用的是補充 1 的銀杏散步地圖；「檢視變更」面板照 Codex app 官方文件畫成示意，commit 編號、Codex 對話和測試案例也是示意。
