WEEK 07

像工程師一樣開發：規劃與測試

這週先看軟體工程：瀑布式開發（Waterfall Model）一階一階往下流，錯在需求就得逆流回到最上面；測試驅動開發（TDD）把它切成很多小步，先寫測試、再寫程式，其實就是我們一直在用的 VERIFY.md。接著是 PLANS.md：大任務先規劃，由 Codex 起草、你審方向。補充教材再把自己的網站拆開來看：HTML、CSS、JS 和素材各管什麼，瀏覽器怎麼把它們組起來；以及 Git 的版本管理怎麼成為用 AI 開發時的安全網：先看 AI 改了什麼，改壞了就回到上一個存檔點，測試全綠才 commit。作業：玩老師做的「空中之島」，先自己想好要做什麼、怎樣算做好，再讓 Codex 照 PLANS.md 和你的測試一步一步做出來。

影片 01軟體工程與測試驅動開發（TDD）

  1. AI 寫程式這麼快，為什麼還要軟體工程？軟體工程是一群人在有限的時間裡，做出可靠、以後還改得動的軟體的方法。AI 讓寫程式變快了，難的變成「知道要做什麼」和「確定做對了」，所以軟體工程反而更重要。

  2. 瀑布式開發（Waterfall Model）：一階一階往下流。需求 → 設計 → 實作 → 測試 → 維護。其實你已經跑過一次小瀑布了：BRIEF.md、PLANS.md、Codex 寫程式、VERIFY.md、AGENTS.md。

  3. 問題是測試排在最後。如果錯在需求，就得逆流回到最上面，中間做的全部要重來。最常被引用的瀑布論文（Royce，1970）其實在提醒：只跑一趟「risky and invites failure」。所以業界採用瀑布式開發的，通常是流程很熟、做過很多次、有過去經驗的專案。

  4. 測試驅動開發（Test-Driven Development，TDD）：把一趟大瀑布，切成很多小瀑布。每一小步都是：紅，先寫一個會失敗的測試；綠，寫剛好讓它通過的程式；重構（refactor），把程式整理乾淨，燈要一直是綠的。

  5. 寫測試，就是先寫下「給什麼輸入，應該得到什麼」。一條就是一個測試案例（test case），寫成程式，一個指令全部跑完。是不是很熟悉？這就是我們一直在用的 VERIFY.md。從 Single-turn Prompting 到 VERIFY.md，我們一直強調：先想清楚，結果才有確定性。

  6. 為什麼特別適合 AI：AI 很會說「做好了」，測試不會被說服。回歸（regression）是改了 A，壞了 B：新加「補考」的規則後，原本會過的「請假」測試變紅了；測試每次都全部重跑，B 一壞馬上被抓到。小心 AI 為了通過去改測試，在 AGENTS.md 寫上「不要為了通過而修改測試；覺得測試錯了，先問我」。影片裡的山谷、Codex 畫面和成績都是示意。

影片 02大任務，先規劃：PLANS.md

  1. PLANS.md 回答「怎麼走到那裡」。AGENTS.md 是怎麼做事，BRIEF.md 是做什麼，VERIFY.md 是怎樣算做好（你寫、你維護）；PLANS.md 寫分幾步、先做什麼、每一步要通過哪幾條測試，交給 AI 寫，你審方向。檔名全大寫是大家約好的名字，看到就知道用途；小寫是你自己取的。

  2. 哪句是 BRIEF、哪句是 PLANS？誰來做都一樣的（目的、限制，例如世界大小固定）寫在 BRIEF，很少改；換個人可能不同的（順序、做法、檔案怎麼放）寫在 PLANS，由 AI 邊做邊調整。

  3. 請 Codex 起草之前，先說清楚範圍和驗收。有不清楚的先問你；VERIFY.md 每一條都要排進某一步，每一步寫出要通過哪幾條；不做 BRIEF 沒要的，不違反限制。怎麼做、分幾步，讓 AI 決定。這就是你控制規劃方向的方法。

  4. Plan mode 和 PLANS.md。Codex 的 Plan mode 讓你先看計畫、再放行寫程式；但計畫只在對話裡，開新對話或被壓縮就不見了。寫成 PLANS.md 存在資料夾，換對話也還在。

  5. 你審方向，不用自己改寫。AI 的第一版另存成 PLANS.v1.md 對照用，再問三件事：VERIFY 每一條都排進去了嗎？每一步都對到測試嗎？有沒有偷加 BRIEF 沒要的？不對就請 AI 改。VERIFY.md 是你的，PLANS.md 是 AI 的。

  6. 用 AGENTS.md 守住方向。VERIFY.md 不要改，那是我的；PLANS.md 你可以自己調整，回報時說改了什麼；一次只做一步：先寫測試、確認失敗，再寫程式（影片 01 的 TDD）；不要為了通過而修改測試。之後每一輪只要說「做 PLANS.md 的下一步」；發現 bug 或想到新點子，你先寫進 VERIFY.md。

這週的作業：玩一玩老師做的「空中之島」，然後自己規劃、自己做出一個。重點是你先想清楚要做什麼、怎樣算做好，再讓 Codex 照你的計畫和測試一步一步做；不是把整件事丟給 AI。

素材：下載 sky-island-assets.zip（範例用到的方塊材質和圖示，16×16 像素，附放大版和說明）。範例可以直接在上面玩，也可以開新分頁全螢幕玩。

限制（每個人都一樣，貼進 BRIEF.md）：靜態網站（HTML、CSS、JavaScript），用 three.js 畫 3D，不用伺服器、帳號或遊戲引擎；學校的舊電腦（內顯，或只用 CPU）全螢幕也要每秒 30 格以上；世界大小固定，32 × 32 × 32 格以內，不做無限世界、不做多人；材質只用上面的素材包。

  1. 先玩，再自己寫 BRIEF.md。把範例玩一遍（WASD 走、空白鍵跳、左鍵挖、右鍵放），用你自己的話寫：要做什麼、不做什麼、一個你自己的點子（例如會下雨、可以種花），最後貼上上面的限制。這一份不要請 AI 寫。

  2. 自己想測試：VERIFY.md 的「我的測試」。把玩的時候看到的寫下來，一條一句「我做了什麼 → 應該看到什麼」，至少 5 條，三種都要有：主要功能（「對草地按左鍵 → 那一格不見」）、不可以發生的事（「對著空氣按右鍵 → 不會憑空出現方塊」）、你的點子。要具體到看得出對錯，「放方塊要正常」太模糊。寫完先 commit，再請 Codex 檢查：哪幾條太模糊、測不出來（它提建議，你同意才改）；接著請它把漏掉的補在「AI 補充」區，包括上面的限制，你決定留哪些。

  3. 請 Codex 起草 PLANS.md，你來審方向。先不要寫程式。PLANS.md 是 AI 的：分幾步、什麼順序、怎麼做，讓它決定。你只跟它說清楚範圍和驗收：有不清楚的先問你；VERIFY.md 每一條都要排進某一步，每一步寫出要通過哪幾條；不做 BRIEF 沒要的，不違反限制。AI 的第一版存成 PLANS.v1.md 對照用。你審三件事：每條測試都排進去了嗎？每一步都對到測試嗎？有沒有偷加 BRIEF 沒要的東西？不對就請它改，你不用自己改寫。

  4. 用 AGENTS.md 把規則講好。至少寫進這幾條：不要讀取或複製範例網站的原始碼；VERIFY.md 不要改，那是我的；PLANS.md 你可以自己調整，回報時說改了什麼，但不能做 BRIEF 沒要的；一次只做一步，做完停下來回報；每一步用 TDD：先把這一步的測試寫好、跑一次確認失敗、commit，再寫程式，全部測試通過才 commit，並在 PLANS.md 勾掉這一步；不要為了通過而修改測試。

  5. 一步一步做，你負責看，也繼續維護 VERIFY.md。每一輪只要說「做 PLANS.md 的下一步」。做完看三件事：回報裡新測試是不是先失敗、最後全部通過；寫程式的那次有沒有改到測試檔（用「檢視變更」看）；自己玩一下，把「手動」那幾條打勾。玩的時候發現 bug 或想到新點子，你自己先把它寫進 VERIFY.md，再請 Codex 寫成測試、確認失敗，然後修好或做出來。

  6. 交作業。把你的 GitHub repo 連結交給老師，裡面要有 BRIEF.md、VERIFY.md、PLANS.v1.md、PLANS.md、AGENTS.md、測試和程式。評分最看重你自己想的部分：BRIEF，和你維護的 VERIFY.md（一開始自己寫的「我的測試」要比 PLANS.v1.md 先 commit；後來陸續加的；AI 建議你留下或劃掉的），再加上 git 看得出每一步都先寫測試、再寫程式。成品做到第幾步都可以，但做了的每一步都要有測試通過。

補充 1網站是怎麼組成的

  1. 網站像一棟房子。HTML 是隔間：網站的結構和內容（index.html）；CSS 是裝潢：顏色、排版，還有手機版怎麼排（style.css）；JS 是水電和開關：按了會怎樣、地圖、讀資料（app.js），會動、按了有反應，就是 JS 的強項；再加上素材：圖片，還有 CSV、JSON 這些資料。

  2. 拆開自己的網站，就知道每一塊管什麼。拿掉 CSS，內容都還在，只剩瀏覽器預設的樣子，一排一排的字；拿掉 JS，地圖不見了，按鈕按了也沒反應；兩塊都拿掉，剩下的就是 HTML 的隔間和內容。

  3. 網站就是一個資料夾。入口預設叫 index.html：瀏覽器先拿到它，它再把 CSS、JS、圖片、資料一起拉進來。上線，就是把這個資料夾放到網路上。

  4. 瀏覽器就是網頁的「編譯器」。第一堂課裝 Python，是為了讓電腦有能執行 Python 的「編譯器」，把程式碼翻譯給電腦執行（嚴格說，Python 用的是「直譯器」）。做網站不用另外裝：瀏覽器讀 HTML、CSS，執行 JS，裡面是排版引擎和 JS 引擎，有瀏覽器就看得到結果。

  5. 靜態像印好的菜單，動態像現點現做。靜態網站也能互動。Week 6 的考試是靜態網站：進度存在你的瀏覽器裡，換一台電腦就不見了；要跨裝置同步，才需要伺服器和資料庫。

  6. 懂了網站的組成，才控制得住 AI。指令會更準，例如「只改 style.css，不要動 HTML 結構」；出問題時知道是哪一塊（跑版找 CSS、內容寫錯找 HTML 或資料、按了沒反應找 JS）；也知道登入、全班共享資料這些事，需要伺服器。影片裡的示範網站和 Codex 畫面是示意。

補充 2Git：版本管理，也是你的安全網

  1. Git 最重要的是版本管理。沒有版本管理的時候，檔案只能存成「報告_final_v2_真的最終.docx」，哪一份是最新的、改了什麼，都很難說。用 Git，每次 commit 就是一個存檔點：可以看歷史、比較差異，回到任何一版。GitHub 只是把這些版本放到雲端。

  2. AI 一次會改好幾個檔案，先看它改了什麼。影片裡三張描圖紙就是網站的三個檔案（index.html、style.css、app.js），疊起來就是網站；AI 一次在三張上都改了。Codex app 的「檢視變更」會列出這一輪改了哪些檔案：紅色是刪掉的，綠色是加上的；選「最近一輪」，就只看 AI 這一次改的。專案要是 Git 倉庫，才看得到。

  3. 改壞了很正常，回到上一個存檔點就好。直接跟 AI 說：「剛剛這一輪把地圖弄壞了，請還原這一輪的修改，回到上一個 commit。」三個檔案的改動會一起擦掉，網站回到上一個存檔點。

  4. 測試全綠就 commit，說明要寫清楚。跑測試有紅燈，就請 AI 修，再跑一次；全部通過再 commit。說明寫做了什麼、結果怎樣，例如「地圖加上散步路線規劃，測試全部通過」，而不是「update」，之後看歷史、要回去的時候，才找得到這一版。

  5. 影片裡的畫面是示意。示範用的是補充 1 的銀杏散步地圖；「檢視變更」面板照 Codex app 官方文件畫成示意，commit 編號、Codex 對話和測試案例也是示意。
